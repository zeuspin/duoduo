# 直播间分组与受控调度设计

## 1. 背景与目标

随着直播间数量增加，不同直播间的分析目的、解析规则和访问节奏产生差异。当前系统按房间独立绑定解析器，并对全部未监看房间安排状态检测，容易扩大页面访问量，也缺少清晰的组织边界。

本期目标：

1. 用户可以创建分组并通过拖动或菜单移动直播间。
2. 每个直播间必须且只能属于一个分组，每组最多 9 个直播间。
3. 解析器改为组级绑定，移除房间级绑定。
4. 解析器创建后不可修改，可以阅读、复制新建和删除。
5. 用户可以自由切换查看分组，但全局同一时间最多一个分组运行。
6. 只有运行组执行自动轮询；其他组只能由用户手动刷新。
7. 所有页面状态探测进入同一个串行、去重、带冷却的访问队列。
8. 组停止时取消后续轮询并安全结束该组全部实时记录。

本期不实现组级 Agent、每日总结或 RAG。未来能力只依赖本期提供的稳定组 ID、房间 ID、解析器 ID 和运行实例 ID，不在当前界面放置入口。

## 2. 术语

### 当前查看组

用户正在界面中查看的分组。可以自由切换，切换本身不发起网络请求，也不改变后台运行状态。

### 运行组

正在执行自动状态轮询的分组。全局最多一个。运行组最多包含 9 个直播间，因此系统最多允许该组的 9 路实时监看同时存在，不设置额外并发阈值。

### 组运行实例

一次从“启动”到“停止或失败”的完整运行周期，使用稳定的 `group_run_id` 标识。它用于隔离迟到任务、诊断调度过程和关联后续数据。

## 3. 范围拆分

### 第一阶段：分组和解析器

- 分组的创建、重命名和删除。
- 添加直播间时选择分组。
- 通过拖动或菜单移动直播间。
- 组容量限制。
- 组级解析器选择。
- 不可变解析器的创建、阅读、复制新建和删除。
- 现有房间、解析器和绑定关系迁移。

### 第二阶段：受控调度

- 全局唯一运行组。
- 组的启动、停止和刷新状态。
- 全局串行探测队列。
- 去重、优先级、房间冷却和任务合并。
- 自动监看触发边界。
- 停止收尾、异常恢复和应用重启行为。

## 4. 用户操作流程

### 4.1 创建分组

1. 用户点击“新建分组”。
2. 输入 1–30 个字符的唯一组名。
3. 可选择一个解析器，也可暂不选择。
4. 创建后的分组为“已停止”，不会自动运行或访问页面。

所有分组在权限、容量和调度规则上完全平等，不存在具有特殊业务语义的“默认分组”。首次启动或迁移时系统可以创建普通的起始分组。至少保留一个分组；当存在其他分组时，起始分组与其他组一样可以改名或在空置、停止后删除。

### 4.2 添加直播间

新增直播间时必须使用用户当前查看的分组作为初始目标，不得重新选择列表第一项或静默回退到任何起始分组。添加弹窗明确显示目标组，用户可以主动改选其他未满且停止的分组。当前组运行中或已满时分别给出准确提示，不自动改投其他组。不存在“未分组”状态，`groupId` 是前后端新增请求的必填字段。

### 4.3 移动直播间

用户可以：

- 拖动卡片到另一个分组标签；或
- 从卡片菜单选择“移动到分组”。

两种入口调用同一个后端事务。运行组的直播间不能拖入、拖出或删除；两个停止组之间可以移动，即使另一个组正在运行。目标组达到 9 个时不可接收。

移动成功立即持久化。移动后房间使用目标组解析器，不保留房间级解析器关系。

### 4.4 查看和运行

- 用户可以自由切换当前查看组。
- 顶部持续显示运行组和“查看运行组”。
- 没有运行组时，任一停止组均可启动。
- 已有运行组时，其他组的启动按钮禁用，并显示需要先停止的组名。
- 运行组不能修改成员、解析器或被删除。

### 4.5 启动

点击“启动”后，系统原子创建组运行实例，并仅为该组建立定时轮询。组内房间仍按照各自的直播时间和检测间隔规则安排任务。

探测发现开播后，仅当以下条件同时成立才启动实时记录：

```text
最新状态为开播
AND 房间开启“开播后自动监看”
AND 房间仍属于任务对应分组
AND 该分组仍有有效运行实例
AND 运行实例未收到停止请求
```

### 4.6 停止

点击“停止”后：

1. 运行实例进入 `stopping`。
2. 取消尚未开始的定时探测任务。
3. 不再接受新的自动监看。
4. 已在执行的探测允许结束并保存状态，但不能触发实时记录。
5. 并行安全关闭该组全部实时记录，完成 ASR 收尾和用量记录。
6. 全部结束后运行实例进入 `stopped`，释放唯一运行位。

如果部分实时记录关闭失败，运行实例进入 `stop_failed`，仍占用唯一运行位。界面列出失败房间并提供“重试停止”，不能直接启动其他组。

### 4.7 手动刷新

当前查看的任意组均可刷新，不要求它是运行组。

- 组刷新按卡片显示等待、检查中、完成、复用冷却结果或失败。
- 同一组同时只有一个刷新批次，重复点击复用现有批次。
- 单房间刷新优先于组刷新。
- 非运行组刷新只更新状态，不触发自动监看。
- 运行组刷新与定时轮询使用相同结果处理逻辑，可以按房间开关触发自动监看。

## 5. 界面设计

采用现有桌面端的信息层级：

- 左侧保持现有导航。
- 页面顶部显示运行组、运行状态和“查看运行组”。
- 标题下方使用分组标签，显示组名、状态和容量，例如 `行业研究 · 已停止 · 4/9`。
- 组内容区包含“启动”“停止”“刷新状态”和更多菜单。
- 运行状态不能只用颜色表示，必须有文本和图标。
- 卡片保留房间级“开播后自动监看”。
- 卡片提供拖动把手及“移动到分组”菜单。
- 刷新过程中显示批次进度及每张卡片的队列状态。

主要提示：

- 组已满：`“行业研究”已达到 9 个直播间上限`
- 运行组成员变更：`请先停止“盘中观察”再调整直播间`
- 启动冲突：`“盘中观察”正在运行，同一时间只能启动一个分组`
- 冷却复用：`刚刚已更新`
- 部分失败：`完成：7 成功，2 失败`
- 停止失败：展示未正常结束的直播间并提供重试。

## 6. 数据模型

### 6.1 `room_groups`

```text
id TEXT PRIMARY KEY
name TEXT NOT NULL UNIQUE
parser_id TEXT NULL REFERENCES parsers(id)
position INTEGER NOT NULL
created_at TEXT NOT NULL
updated_at TEXT NOT NULL
```

### 6.2 `rooms` 变更

```text
group_id TEXT NOT NULL REFERENCES room_groups(id)
position_in_group INTEGER NOT NULL
```

保留房间级 `auto_monitor_on_live`、直播时间和检查间隔。移除房间级解析器绑定作为运行时来源。

组容量不能只由前端校验。新增和移动房间必须在同一数据库事务中检查目标组数量并写入，超过 9 时返回 `GROUP_ROOM_LIMIT_REACHED`。

### 6.3 `group_runs`

```text
id TEXT PRIMARY KEY
group_id TEXT NOT NULL REFERENCES room_groups(id)
status TEXT NOT NULL
started_at TEXT NOT NULL
stop_requested_at TEXT NULL
completed_at TEXT NULL
error TEXT NULL
```

状态：

- `starting`
- `running`
- `stopping`
- `stopped`
- `start_failed`
- `stop_failed`
- `interrupted`

数据库使用部分唯一索引或等价事务约束，确保 `starting`、`running`、`stopping`、`stop_failed` 中全局最多存在一条记录。

### 6.4 探测访问状态

持久化每个房间最后一次真实访问尝试时间，不能只使用成功快照时间：

```text
room_probe_access
- room_id PRIMARY KEY
- last_started_at
- last_completed_at
- last_result
```

该记录用于跨重启执行 60 秒房间冷却。

### 6.5 不可变解析器

解析器保存完整规则快照：

```text
id TEXT PRIMARY KEY
name TEXT NOT NULL
spec_json TEXT NOT NULL
created_at TEXT NOT NULL
deleted_at TEXT NULL
```

- 创建完成后不可更新 `spec_json`。
- “复制新建”读取旧快照并生成新 ID。
- 删除使用软删除。
- 被任一组引用时禁止删除，并返回使用组列表。
- 历史观点继续引用原解析器 ID。

## 7. 调度架构

### 7.1 `GroupRunService`

职责：

- 原子启动唯一运行组。
- 为运行组建立和取消定时调度。
- 控制运行实例状态转换。
- 停止组内实时记录并处理失败重试。
- 应用启动时把未完成实例标记为 `interrupted`。

### 7.2 `ProbeOrchestrator`

所有可能访问直播间页面的状态探测必须通过统一入口：

```text
ProbeTask
- roomId
- groupId
- source: scheduled | group_refresh | room_refresh
- groupRunId（scheduled 必填）
- priority
- requestedAt
```

职责：

- 全局探测并发固定为 1。
- 按 `room_id` 合并待执行任务。
- 手动请求提升已有任务优先级，不重复创建。
- 同一房间两次真实访问至少间隔 60 秒。
- 不同房间的最小访问间隔由内部策略控制，第一版不暴露给用户。
- 遇到平台验证或疑似风控时暂停整个队列。
- 提供组刷新批次进度。

优先级：

```text
单房间刷新 > 组级刷新 > 运行组定时轮询
```

### 7.3 迟到结果保护

探测完成后必须重新读取房间、分组、运行实例和自动监看开关。不能依据提交任务时的旧对象触发监看。

`groupRunId` 是定时任务的代际标识。旧实例的迟到结果可以更新可信状态，但不得作用于新实例或启动实时记录。

### 7.4 实时监看边界

- 不设置额外并发阈值。
- 最多允许运行组的 9 个房间同时实时监看。
- 不允许跨组叠加自动监看。
- 只有运行组允许用户手动点击“加入实时监看”；停止组按钮禁用并提示先启动当前分组。
- 后端继续校验房间所属组与当前运行实例；若前端快照过期，拒绝结果转为用户可见提示并刷新状态，不产生未处理 Promise。
- 非运行组的手动刷新不触发实时监看。
- 9 路场景必须进行资源、ASR 关闭和 AI 用量压力测试。

### 7.5 直播间公开指标采集与卡片展示

- 粉丝数只能来自直播页可见文本、无障碍属性、结构化数据或用户资料浮层中的原始证据，不允许推断。
- 资料浮层采集不能只依赖 `aria-describedby`；依次尝试已有浮层、hover/click 主播入口和当前可见的 dialog、tooltip、popover、profile 容器。
- 采集过程记录 `trigger_missing`、`popup_missing`、`followers_missing` 或 `found`，便于区分页面结构变化与解析失败。
- 直播监看卡片第一行显示完整标题和操作按钮，第二行只显示“主播粉丝”和“当前在线/上次在线”。标签区域不重复展示在线人数。

## 8. 解析器流程

原有“草稿—发布—房间绑定”改为：

1. 新建解析器。
2. 编辑名称、目标、过滤规则、模型和高级提示词。
3. 选择直播间样本运行测试，可以重复测试。
4. 点击“创建并保存”后冻结。
5. 详情页只能阅读、复制新建或删除。

停止组可以选择或取消解析器。运行组不可修改。实时分析通过 `room → group → parser` 解析规则。组未选择解析器时只保存 ASR，不生成观点。

## 9. 数据迁移

### 9.1 房间迁移

- 现有房间不超过 9 个：创建一个普通起始分组。
- 超过 9 个：按房间创建时间拆成多个普通起始分组。
- 每组最多 9 个。
- 第一组仅作为初始查看项，不具有特殊业务权限，也不存在运行组。
- 原 `monitoring=true` 不恢复，所有组迁移后均已停止。
- 应用升级启动不会自动访问页面。

### 9.2 解析器迁移

- 现有默认解析器作为普通用户解析器，不保留“系统内建”属性。
- 每个已发布版本冻结为一个独立解析器。
- 未发布草稿不进入正式解析器列表。
- 原房间级绑定不自动推断组级解析器，迁移后的组默认不绑定解析器。
- 历史观点仍能读取原解析器定义。

## 10. 应用重启与异常恢复

- 启动时把未完成的组运行实例标记为 `interrupted`。
- 不自动恢复轮询和实时记录。
- 所有组显示已停止，并提示上一次运行异常中断。
- 用户必须重新点击启动才会产生访问。
- 原可信房间状态保留，不因重启变为离线或未知。
- 房间冷却记录继续有效，不能通过重启绕过。

## 11. 风控边界

本设计不能保证永远不会触发平台防护，因为平台阈值未公开。它从结构上消除以下明显漏洞：

- 多组同时自动轮询。
- 多个页面状态探测并发。
- 重复点击制造重复访问。
- 单房间手动刷新绕过 60 秒冷却。
- 应用重启清空冷却。
- 停止后的迟到结果重新启动监看。
- 非运行组通过手动刷新启动自动监看。

平台验证、登录要求或疑似风控出现时，沿用现有全局访问暂停和人工恢复流程。恢复后任务重新排队，不集中补跑过期任务。

## 12. 错误处理

- 后端事务拒绝超过容量、运行组成员变更和双运行实例。
- 前端收到冲突后回滚拖动位置并刷新分组快照。
- 探测失败保留已有可信状态，不用失败结果覆盖为离线。
- 组刷新允许部分成功，并展示逐房间结果。
- 停止失败保留运行位，支持幂等重试。
- 删除被引用解析器时返回使用组列表。
- 删除组不会级联删除直播间；非空组直接拒绝。

## 13. 验收标准

### 分组和解析器

- 每个房间始终关联一个有效组。
- 数据库无法通过并发移动突破每组 9 个上限。
- 运行组不能修改成员或解析器。
- 拖动和菜单移动产生相同持久化结果。
- 新增直播间必须选择未满组。
- 非空组和当前运行组不能删除。
- 解析器创建后不能修改。
- 被组使用的解析器不能删除。
- 复制新建生成独立解析器。

### 调度

- 全局无法同时存在两个有效运行实例。
- 未运行组不产生定时任务。
- 用户可以自由切换查看组，不改变运行组。
- 非运行组手动刷新不会触发自动监看。
- 运行组探测发现开播后按房间开关触发监看。
- 停止请求后的迟到结果不会触发监看。
- 同一房间 60 秒内不会发生第二次真实页面访问。
- 手动任务可提升优先级但不重复创建。
- 平台验证会暂停整个队列。
- 应用重启后不自动恢复运行。

### 稳定性

- 9 路实时记录可以完成启动、运行、停止和 ASR 用量收尾。
- 停止失败可以幂等重试。
- 迁移后所有房间均有分组且没有自动页面访问。
- 全量类型检查、单元测试、集成测试和 Electron 构建通过。

## 14. 明确不做

- 一个直播间属于多个组。
- 组标签或多维分类。
- 多个运行组。
- 组级 Agent、每日总结和 RAG。
- 自动恢复上次运行组。
- 用户配置探测并发或访问节流参数。
- 独立于组容量的实时监看并发上限。
