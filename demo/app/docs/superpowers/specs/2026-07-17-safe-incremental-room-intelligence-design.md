# 安全增量直播间画像与透明标签设计

## 1. 背景与目标

第一阶段已经建立预备直播间串行检测、人工验证码恢复、可信状态保存和卡片操作反馈，但尚有三类缺口：

1. 实时监看启动与自动重连仍可绕过统一抖音访问协调器，验证码保护不能覆盖所有导航入口。
2. 离线页面已经下载的初始头像没有写入数据库；离线时手动更新头像也会被资料保护规则忽略。
3. 在线人数、粉丝数等指标虽然已有字段，但当前真实数据库没有有效数值，无法可靠判断主播规模和近期热度。

本阶段目标是在不增加抖音页面访问次数的前提下完成第一阶段收口，并利用以后自然发生的状态检测和已打开直播页面逐步积累本地画像数据，提供可解释的透明标签、趋势和开停播详情。

## 2. 已确认的产品决策

- 数据获取采用“安全增量采集”：不主动补抓历史、不为标签创建额外页面、不提高更新频率。
- 主播规模采用绝对粉丝量级；近期热度结合主播自身历史和本地直播间列表相对位置。
- 卡片采用透明标签，不使用无法解释的综合分数。
- 头像默认只在首次可信获取时保存；以后只有用户点击“更新头像”才能替换。
- 数据不足时明确显示“数据积累中”，缺失值不能当作 0。
- 所有页面导航继续受验证码暂停、全局串行、冷却、节流和退避保护。
- 不新建分支、不提交、不推送。

## 3. 范围

### 3.1 包含

- 修复并迁移本地头像路径，不访问抖音即可恢复已经缓存的头像。
- 将实时监看启动、离线重试和技术重连接入统一访问协调器。
- 为所有新页面导航增加全局最小间隔和自动访问预算。
- 改进现有页面内指标提取，并记录指标来源与数据质量。
- 已打开的监看页面按低频节流读取现有 DOM 指标，不刷新或重新导航。
- 基于本地观察记录和直播场次计算透明标签。
- 卡片展示核心指标和最多三个标签；详情抽屉展示证据、趋势和开停播区间。
- 本地 fixture、单元测试和 Electron E2E；自动化验收不访问真实抖音。

### 3.2 不包含

- 不自动识别、点击、代答或绕过验证码。
- 不读取 Cookie、输入框内容、验证码答案或用户键盘事件。
- 不抓取抖音全平台排名，不声称标签代表全平台结论。
- 不使用额外隐藏页面补齐粉丝数、在线人数或历史数据。
- 不根据缺失区间推测精确开播或停播时间。
- 不把标签阈值做成第一版用户可配置规则引擎。

## 4. 风控边界与访问预算

### 4.1 单一导航边界

所有可能产生抖音主框架导航的入口必须提交给 `DouyinAccessCoordinator`：

- 启动检测、周期检测、卡片单独检测和“更新全部”。
- 首次头像获取所伴随的既有状态检测、用户手动更新头像。
- 实时监看首次启动、离线等待后的重试、技术故障后的重连。
- 用户点击播放。
- 人工验证恢复检查继续只读取当前验证页，不产生新导航。

创建窗口或视图不能提前导航。协调器允许任务开始后才能创建或加载远端页面；任务排队期间不得预先占用新的抖音页面。

### 4.2 节流和退避

- 自动导航全局预算默认最多 10 次/小时。
- 任意两次新抖音导航默认至少间隔 60 秒；用户明确播放可取得优先级，但不能绕过验证码暂停和最小间隔。
- 预备直播间可信离线后按 30、60、120 分钟退避，持续离线后保持 120 分钟。
- 超时、页面错误和登录阻塞按至少 30、60、120 分钟退避，不进行快速技术重试。
- 已知直播中房间的状态导航不得快于 10 分钟；若直播页面已经处于监看状态，则只在该页面内读取状态和指标，不另开检测页。
- “更新全部”进入同一节流队列，显示预计完成时间并允许取消，不形成短时批量导航。
- 验证码或疑似验证码立即清空未开始队列并持久化暂停状态；恢复后不自动重放旧队列。

预算用于降低访问风险，不能保证平台永远不触发安全验证。UI 必须如实显示节流、排队和暂停状态。

## 5. 可信资料与头像修复

资料持久化不再使用单一的 `status === live` 开关，而是按字段区分：

- 主播名、标题和封面：只允许可信直播结果更新；离线通用标题不能覆盖既有资料。
- 初始头像：可信 `live` 或 `offline` 结果都可保存，但仅在数据库尚无头像路径时写入。
- 手动头像更新：用户明确点击后，可信 `live` 或 `offline` 页面获取到的头像可以替换现有头像。
- `verification_required`、`login_required`、`timeout`、`page_error` 和 `checking` 均不能写入头像或主播资料。

新增本地一致性修复：启动时检查应用自有 `avatars/<roomId>.png`。若文件是有效图片且数据库头像路径为空，则只补写路径，不发起网络请求。该修复用于恢复“老刘看财经”和“严王财经”等已经下载但未关联的头像，也适用于同类历史记录。

## 6. 安全增量指标采集

### 6.1 采集时机

指标只能从两类已经存在的页面读取：

1. 原本就要执行的状态检测页面，在得到可信结果时解析一次。
2. 已经打开并正在监看的直播页面，最多每 5 分钟读取一次当前 DOM；读取不刷新、不跳转、不创建请求。

卡片渲染、标签计算、详情打开、排序、筛选和数据导出都只能访问本地数据库。

### 6.2 指标与质量

第一版记录：

- `viewerCount`：当前在线人数。
- `followerCount`：主播粉丝数。
- `totalViewerCount`：本场累计观看人数。
- `likeCount`：本场点赞数。
- 每项指标的原始显示文本、提取来源和观察时间。

提取来源按可信度排序：明确语义的可见元素、可访问性标签、页面内结构化公开数据、有限正文模式。不得读取网络响应、Cookie、登录信息或验证码相关内容。

只有至少一个数值成功解析时才能设置 `metricsObservedAt` 并写入指标观察记录。空对象 `{}`、缺失文本和无法识别的单位都视为 `missing`，不能制造虚假的“已采集时间”。

同一已打开页面的指标快照至少间隔 5 分钟。若所有数值与上一条相同，可合并为一次心跳或跳过写入，避免数据库膨胀。

## 7. 本地分析模型

主进程新增纯本地的 `RoomIntelligenceService`。它只读取 `room_snapshots`、`room_observations` 和 `live_sessions`，输出卡片摘要和详情，不依赖访问协调器，不持有 Electron 页面。

建议输出结构：

```ts
interface TransparentLabel {
  kind: "audience_scale" | "recent_heat" | "growth" | "activity" | "duration" | "insufficient_data";
  text: string;
  explanation: string;
  observedAt?: string;
  sampleCount: number;
  comparisonCount?: number;
}

interface RoomIntelligence {
  roomId: string;
  generatedAt: string;
  currentMetrics: {
    viewerCount?: number;
    followerCount?: number;
    totalViewerCount?: number;
    likeCount?: number;
    observedAt?: string;
  };
  labels: TransparentLabel[];
  sevenDay: RoomPeriodSummary;
  thirtyDay: RoomPeriodSummary;
  sessions: RoomSessionSummary[];
}
```

所有计算均使用自然时间窗口和可信数值；不可用状态、空指标和验证页面不进入统计。

## 8. 透明标签规则

卡片最多展示三个有效标签，按规模、热度、活跃度排序：

### 8.1 粉丝规模

- `千万级粉丝`：最新可信粉丝数 ≥ 1,000 万。
- `百万级粉丝`：100 万至 999.9 万。
- `十万级粉丝`：10 万至 99.9 万。
- 低于 10 万继续显示具体粉丝数，但不生成规模结论标签。

规模标签必须显示指标观察时间；离线卡片标记为“上次采集”。

### 8.2 近期热度

- `近期在线靠前`：最近 7 天按直播场次聚合后的平均在线人数位于本地可比较主播前 25%。至少需要本房间 2 场有指标直播、总计 5 个可比较主播。
- `近期升温 +N%`：最近 7 天场次平均在线人数相对之前 7 天增长至少 30%，且绝对增长不少于 100。两个窗口各至少需要 2 场有指标直播。
- 单场当前在线突增只显示当前人数，不直接生成“近期升温”，避免把瞬时波动当趋势。

相对标签的说明必须写明“本地 N 个有数据主播中”，不能暗示抖音全平台排名。

### 8.3 开播活跃度与时长

- `近7日开播N天`：最近 7 个自然日中存在可信直播证据的天数；N ≥ 3 时展示。
- `已观测长播`：至少 3 个已结束场次的已观测时长中位数 ≥ 2 小时。

开播和停播时间使用证据区间表达：上次离线证据、首次直播证据、最后直播证据、首次离线证据。第一版不推断不可观测区间内的精确时间。

### 8.4 数据不足

没有任何有效粉丝、在线或场次指标时显示一个中性 `数据积累中` 标签。部分维度缺失时只隐藏该维度标签，不影响已有可信标签。

## 9. 卡片与详情交互

### 9.1 卡片

- 保留主播名、头像、直播状态、封面、操作按钮和数据新鲜度。
- 直播中突出当前在线人数；离线时显示上次可信粉丝数及采集时间。
- 在标题和时间信息之间增加最多三枚透明标签。
- 每枚标签支持鼠标悬停、键盘聚焦和点击说明；提示内容包含公式、窗口、样本数、比较房间数、数据时间和本地样本声明。
- 增加文字化“查看详情”入口；打开详情不能触发检测。

### 9.2 详情抽屉

详情抽屉包含：

1. 当前状态、最后可信状态、最近尝试状态和各自时间。
2. 当前或上次可信指标，以及指标采集时间和质量。
3. 最近 7 天与 30 天的在线人数趋势；无数据时展示缺失原因。
4. 直播场次列表：开播证据区间、停播证据区间、峰值、平均值和已观测时长。
5. 所有标签的完整判断依据。

趋势图按时间显示原始可信快照，不插值缺失区间，不把停播补成在线人数 0。

## 10. 数据接口与存储

- 保留现有观察表和直播场次表，按需增加指标来源与去重字段；不另存标签结果，避免阈值调整后出现旧标签。
- 标签在查询时从本地事实计算；可在主进程内短期缓存，数据库变化后失效。
- 新增只读 IPC：批量卡片摘要、单房间详情。IPC handler 不得引用 `DouyinAccessCoordinator.submit`、`probeRoom`、`BrowserWindow` 或 `WebContentsView`。
- 详情查询限制返回窗口和点数，避免一次加载全部历史；7/30 天趋势按合理粒度聚合。
- 现有数据清理继续作用于原始观察和汇总数据；删除历史后标签必须自动按剩余数据重算。
- 备份导入导出继续包含数据库和头像；标签无需单独备份。

## 11. 错误与边界行为

- 指标提取失败不改变直播状态，也不清空旧指标。
- 头像本地修复失败只记录诊断，不阻止应用启动。
- 标签计算异常只影响对应房间并降级为“数据暂不可用”。
- 验证暂停期间，卡片和详情仍可读取并展示旧的本地数据，但必须显示数据可能过期。
- 数据清理、导入或迁移后，详情服务必须处理空历史和部分历史。
- 用户连续打开不同详情不得创建页面、导航或新的长期定时器。

## 12. 实施顺序

1. 第一阶段 1.1 收口：导航协调、节流预算、验证码恢复 fixture E2E。
2. 头像持久化修复和本地缓存路径迁移。
3. 指标质量语义和安全增量提取，先用本地 fixture 验证。
4. 本地画像查询服务与透明标签规则。
5. 卡片标签、提示和详情抽屉。
6. 全量回归、构建、密钥扫描和无真实抖音访问的验收报告。

第二阶段代码只有在第 1 步通过后才能接入 UI，避免在仍有导航旁路时扩大功能面。

## 13. 验收标准

### 13.1 风控与导航

- 静态审计确认所有抖音导航入口通过协调器。
- 本地 E2E 证明并发为 1、最小间隔和自动预算有效。
- 监看启动或重连命中验证码后立即进入全局暂停，旧队列不重放。
- 标签、详情、趋势、排序、筛选和头像本地迁移测试均断言没有调用页面访问接口。
- 自动化验收不连接真实抖音；真实低频检查必须再次获得用户明确授权。

### 13.2 头像

- 已存在头像文件但数据库路径为空时，重启应用后自动恢复显示。
- 可信离线首次获取可保存头像；以后普通状态更新不替换头像。
- 离线时用户手动更新头像可以替换；失败时旧头像仍保留。
- 验证码、登录、超时和错误页面不能写入头像。

### 13.3 数据与标签

- 空指标不会产生 `metricsObservedAt`，也不会被统计为 0。
- 新指标只伴随既有导航或已打开页面采集，不产生额外页面。
- 标签规则、最小样本、自然时间窗口和百分位比较有确定性单元测试。
- 卡片最多三个标签；每个标签均能查看证据、时间和样本数。
- 现有真实数据库在没有有效人数指标时只显示“数据积累中”，不产生错误热度结论。
- 7/30 天趋势不对缺失值插值，开停播展示证据区间。

### 13.4 工程验证

- 相关测试先失败后通过，完整单元与集成测试通过。
- Fixture Electron E2E、类型检查、构建、密钥扫描和 `git diff --check` 通过。
- 验收报告记录命令、结果、已知限制和真实访问为零。
- 保留用户现有未提交变更，不创建分支、不提交、不推送。
