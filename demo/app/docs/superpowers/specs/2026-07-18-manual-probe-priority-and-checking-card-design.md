# 手动检测优先级与检测中卡片优化设计

## 1. 背景

当前预备直播间使用单通道检测队列，以降低并发访问抖音导致验证的风险。应用启动或执行批量检测时，所有房间会依次进入队列。卡片上的“立即检测”调用同一个调度器，但当前实现遇到以下情况时不会产生符合用户预期的手动检测：

- 房间已经在自动队列中时，手动操作直接复用原任务，不提升优先级。
- 其他房间占用单通道时，新手动任务排在现有自动队列末尾。
- 界面在点击瞬间开始 60 秒冷却，即使任务尚未执行。

真实数据库中的检测记录呈现约每分钟依次处理一个房间，与上述调度行为一致。因此手动点击可能等待较长时间，界面却只显示冷却，表现为“点击无效”。

检测期间，卡片还会把当前状态直接替换为 `checking`，导致直播高亮丢失；卡片名称与操作按钮共用一行，长名称被省略。

## 2. 目标

1. 手动检测在不增加并发页面访问的前提下获得队列优先级。
2. 界面准确区分等待检测、正在检测、检测完成和冷却状态。
3. 检测中保留上一次可信的主播资料、粉丝数和直播状态提示。
4. 直播间名称完整展示，粉丝数与操作按钮共用一行。

## 3. 非目标

- 不增加检测并发数。
- 不绕过抖音访问协调器、访问间隔和验证暂停机制。
- 不中断正在进行的页面检测。
- 不改变粉丝数的采集来源和可信数据保存策略。
- 不修改实时监看列表的主体工作区布局。

## 4. 手动检测调度

### 4.1 队列规则

`ProbeScheduler` 继续保持单通道执行，但待执行任务区分手动和自动优先级：

1. 当前正在执行的任务不会被中断。
2. 新手动任务插入到所有待执行自动任务之前。
3. 同一房间已存在待执行自动任务时，不创建重复任务；将原任务来源升级为 `manual`，移至当前任务之后的最高优先位置。
4. 同一房间已在执行时，复用当前任务并报告“正在检测”。
5. 多个手动任务按用户点击顺序执行。
6. 批量进度仍按原批次统计；被手动升级的任务完成后同时计入原批次完成数。

访问协调器继续负责页面访问节流。手动优先级只改变尚未执行任务的顺序，不提高并发数，也不绕过平台保护。

### 4.2 可观察状态

调度器对渲染进程提供每个房间的检测阶段：

- `idle`：没有手动检测请求。
- `queued`：用户已请求，正在等待当前安全任务完成。
- `running`：本房间页面正在检测。
- `cooldown`：最近一次手动检测已经完成，暂不可重复请求。

现有 `PreparedProbeState` 增加 `manualProbes` 字段，使用以下结构向渲染进程发布房间级状态：

```ts
type ManualProbeState = {
  roomId: string;
  phase: "queued" | "running" | "cooldown";
  cooldownUntil?: string;
};
```

- `queued` 和 `running` 由主进程调度器的真实队列状态生成。
- `cooldown` 的 `cooldownUntil` 由主进程根据任务完成时间生成。
- 不在 `manualProbes` 中的房间视为 `idle`。

渲染进程只负责展示该状态，不能在点击时自行启动或推测冷却。应用重新加载后，也以主进程重新发布的状态为准。

### 4.3 冷却语义

60 秒冷却从手动检测实际完成时开始，而不是从点击时开始。

- 成功得到直播、未开播或受保护状态后进入冷却。
- 检测执行失败时不进入虚假冷却，按钮恢复“立即检测”并显示错误。
- 点击一个已经运行的房间不会重置冷却计时，也不会创建第二个任务。

## 5. 卡片交互状态

检测按钮文案与行为：

- `idle`：`立即检测`，可点击。
- `queued`：`等待检测`，禁用。
- `running`：`正在检测`，禁用并显示旋转反馈。
- `cooldown`：显示剩余秒数，禁用。
- 访问验证暂停：沿用现有禁用规则。

点击后必须很快收到主进程发布的 `queued` 或 `running` 状态。IPC 返回最终检测结果后更新卡片数据；错误通过现有 toast 展示清晰原因。

## 6. 检测中卡片

### 6.1 状态合成

`checking` 是当前操作阶段，不应覆盖上一次可信业务状态。卡片展示时组合：

- 当前阶段：`snapshot.status === "checking"`。
- 上一次可信状态：`snapshot.lastReliableStatus`，可能为 `live` 或 `offline`。
- 上一次可信资料：现有持久化的名称、头像、封面和粉丝数。

图片左上角显示 `检测中`；其下显示 `上次状态：直播中`、`上次状态：未开播`，或在没有可信历史时显示 `正在确认直播状态`。

### 6.2 功能保持

- 数据详情保持可用。
- 播放保持可用，继续遵守现有访问保护。
- 实时监看按钮保持可用。
- 自动监看设置保持可用。
- 检测按钮显示 `正在检测` 并禁用。
- 上一次可信状态为直播中时，实时监看按钮继续使用直播高亮。
- 粉丝数优先使用最新可信的 intelligence 指标，其次使用快照保留值；两者都缺失时显示 `待获取`。

## 7. 正文布局

采用已确认的方案 A 修订布局：

1. 第一行仅显示直播间名称，占满正文宽度，允许自然换行和长单词断行，不使用省略号截断。
2. 第二行左侧显示 `主播粉丝` 与数值，右侧显示播放、检测和更多操作按钮。
3. 第三行显示“加入实时监看”按钮和“开播后自动监看”设置。

标题完整展示优先于保持所有卡片高度完全一致。操作按钮不能挤占标题宽度。

## 8. 错误和边界处理

- 已在运行的房间再次点击只复用任务，不创建重复页面。
- 自动任务升级为手动后保留其原批次归属，避免批量进度永久不完成。
- 验证页面出现时继续停止后续自动队列，并按现有访问暂停流程处理。
- 手动任务排队期间关闭应用，由现有调度器停止流程安全取消。
- 没有上一次可信状态时，检测中不能推断直播或高亮实时监看按钮。
- 名称中包含验证中间页特征时，继续使用现有安全名称过滤逻辑。

## 9. 测试与验收

### 9.1 调度器

- 自动队列执行期间，手动任务成为当前任务后的下一项。
- 同一房间的待执行自动任务被升级而不是复制。
- 正在执行的同房间任务被复用。
- 多个手动任务保持点击顺序。
- 升级任务仍正确推进原批量进度。
- 并发数始终为 1，验证保护保持有效。

### 9.2 渲染交互

- 点击后显示等待或正在检测，而不是立即显示冷却。
- 完成后才开始 60 秒倒计时。
- 失败后恢复按钮并显示错误。
- 检测按钮在等待、运行和冷却阶段均不可重复触发。

### 9.3 卡片展示

- 检测中显示当前阶段和上一次可信状态。
- 上一次直播时保留粉丝数和实时监看高亮。
- 上一次未开播时保留粉丝数但不错误高亮。
- 无可信历史时显示中性检测状态。
- 长名称完整换行显示。
- 粉丝数与操作按钮位于同一行，监看控件位于下一行。

### 9.4 回归

- 单房间自动检测、启动批量检测和手动批量更新仍能完成。
- 自动监看、播放、数据详情、头像更新、编辑和删除保持可用。
- TypeScript、完整单元测试、Electron 构建和 fixture E2E 均通过。
