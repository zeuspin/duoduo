# 直播间资料提取与直播介绍展示设计

## 目标

在一次直播间页面会话内完整提取主播资料和直播指标，修复粉丝数、在线人数缺失的问题，并将部分直播间提供的“直播介绍”作为可选信息保存和展示。

## 已验证的抖音页面结构

以直播间 `https://live.douyin.com/666914142539` 实测：

- 主播名称位于 `data-e2e="live-room-nickname"`。
- 主播头像位于主播信息栏的 `data-e2e="live-avatar"` 内。
- 在线人数位于 `data-e2e="live-room-audience"`，数值会实时变化。
- 主播资料卡触发器为 `data-e2e="rooom-info-bar-anchor"`（抖音页面属性包含三个 `o`）。
- 点击触发器后，可通过其 `aria-describedby` 找到对应资料卡。
- 资料卡可能包含粉丝数、头像、主播名称和“直播介绍”；直播介绍并非所有直播间都有。

## 数据模型

检测结果和房间快照增加可选字段：

```ts
liveDescription?: string
```

该字段只表示抖音主播资料卡中的“直播介绍”，不得写入或替代用户配置的直播时间，也不得解释为本场实际开播时间。

数据库的 `room_snapshots` 增加可空列 `live_description`。历史记录无需新增此字段，因为直播介绍属于主播资料，不是时序指标。

## 提取流程

一次检测只加载一次直播间 URL，并在同一页面中完成以下步骤：

1. 等待直播基础结构出现并判断直播状态。
2. 优先通过稳定的 `data-e2e` 属性读取主播名称、主播头像、在线人数和本场点赞。
3. 若存在主播资料卡触发器，则点击一次。
4. 通过触发器的 `aria-describedby` 精确定位对应资料卡，而不是扫描所有弹层。
5. 从资料卡中提取粉丝数、资料卡头像和可选的直播介绍。
6. 合并首屏和资料卡结果后保存，结束检测页面会话；不得重新导航或重复打开直播间。

资料卡不存在、无法打开或没有直播介绍时，基础状态检测仍应成功，不得因此把直播间标记为检测失败。

## 更新规则

- 本次提取到非空直播介绍时，更新 `liveDescription`。
- 本次未提取到直播介绍时，保留数据库中上一次有效值，避免页面偶发缺失导致信息闪烁或被误清空。
- 只有将来存在明确的“主播已删除介绍”证据时，才考虑清空；本次实现不推断删除。
- 粉丝数和在线人数继续按现有指标时间规则记录，不与直播介绍共用更新时间语义。

## 卡片展示

未监看卡片和已监看卡片使用同一展示规则：

- 放在“主播粉丝 / 操作按钮”一行下方。
- 文案格式为 `直播介绍：{内容}`。
- 最多显示两行，超出部分使用省略号。
- 使用标题提示展示完整内容，便于鼠标悬停查看。
- 字段不存在时不渲染节点，也不保留空白高度。

## 兼容与错误处理

- 首选 `data-e2e` 和 `aria-describedby`，类名仅作为受限降级方案，避免依赖抖音生成式类名。
- 在线人数解析直接读取 `data-e2e="live-room-audience"` 的数值，同时补充对“在线观众 · 数值”文本格式的降级支持。
- 资料卡交互采用短时、有界等待；失败时返回已获得的基础信息。
- 未开播页面没有资料卡时，保留此前已知的主播资料和直播介绍。

## 测试范围

- 能从稳定节点提取在线人数、主播名称和头像。
- 点击资料卡后能提取 `1.2万 粉丝` 和直播介绍。
- 没有资料卡或没有直播介绍时检测仍成功。
- 新检测缺少直播介绍时保留旧值。
- 数据库迁移、读写和共享契约支持可选字段。
- 未监看和已监看卡片均展示直播介绍。
- 长介绍最多两行并提供完整标题；无介绍时不占位。
- 现有检测、监看交接和卡片行为不回归。
