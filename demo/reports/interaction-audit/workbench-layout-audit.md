# 多多直播工作台交互与视觉审计

审计日期：2026-07-11

## 审计范围

本次审计对象为第一轮工作台信息架构视觉稿，覆盖主控台、多频道墙和事件时间线三个方案。审计重点是用户能否理解直播间检测、加入监看、静默内录、单路声音播放、实时 ASR 和未来观点警示之间的关系。

本次审计基于静态视觉稿及方案选择交互。尚未形成完整可操作原型，因此不能验证键盘操作、焦点顺序、加载时延和真实状态切换。

## 用户核心任务

1. 维护直播间，并识别哪些直播间正在直播。
2. 将已开播直播间加入静默监看。
3. 在多路 ASR 持续运行时，选择且只选择一路播放音视频。
4. 在不同直播间之间切换查看与播放，不中断其他直播间的 ASR。
5. 未来从重点警示回到主播、发生时间和 ASR 原文。

## 总体结论

当前视觉稿足以比较信息架构，但还不能作为交互需求确认稿。最大的问题不是视觉风格，而是三个不同概念没有被清楚拆开：

- `选中直播间`：决定主区域当前展示谁的详情。
- `监看直播间`：决定哪些直播间持续内录和 ASR。
- `播放直播间`：决定唯一一路向扬声器播放声音并显示视频。

如果继续沿用当前表达，用户容易把点击直播间理解成开始播放、开始监看或只是查看详情中的任意一种。

## 主要问题

### P0：状态与动作模型不清楚

1. 左侧直播间同时使用“播放中”“静默监看”“未开播”等标签，但没有说明点击整行会执行什么动作。
2. `播放中` 同时可能表示直播平台已开播、客户端正在监看，或正在通过扬声器播放，语义冲突。
3. `＋` 无文字说明，无法判断是添加直播间还是将直播间加入监看。
4. 缺少明确的“加入监看”“停止监看”“播放声音”“停止播放声音”控制。
5. 没有表现切换播放直播间时，原直播间继续静默 ASR 的反馈。

建议采用正交状态：

| 维度 | 状态 |
| --- | --- |
| 平台直播状态 | 检测中 / 未开播 / 已开播 / 不可访问 / 检测异常 |
| 客户端监看状态 | 未监看 / 启动中 / 静默监看 / 监看异常 |
| 前台播放状态 | 未播放 / 播放中 |
| 当前查看状态 | 未选中 / 已选中 |

### P0：核心任务入口不明确

1. 用户最常做的动作是从“已开播”加入监看，但页面没有可见的主操作。
2. 已维护列表与正在监看列表混在同一个区域，数量增多后难以扫描。
3. 当前主控台默认展示视频，使用户可能误以为打开详情就会播放声音。
4. 多频道墙里的“加入监看”与左侧列表管理属于不同层级，却被放进内容网格。

建议左侧采用分组列表：`监看中`、`已开播`、`未开播`。已开播行提供明确的“加入监看”，监看中行提供独立的“播放声音”控制。

### P1：实时 ASR 的状态不足

1. 没有区分实时临时结果和已经确认的 ASR 文本。
2. 没有显示最后收到音频、最后生成文字和当前延迟。
3. 没有表现“有音频但无人说话”“无音轨”“ASR 连接中断”等常见状态。
4. 主控台只展示当前直播间文字，但没有说明其他直播间的 ASR 是否仍在运行。

建议每路显示轻量运行信号：音频活动、ASR 状态、最后文本时间；只在异常时展开技术细节。

### P1：重点警示缺乏可信度结构

1. 警示直接插入 ASR 流，容易被误认为主播原话。
2. 没有明确区分 ASR 原文、AI 提炼和系统判断。
3. 没有“查看上下文”“回到直播间”“标记误报”等后续动作。
4. `重点观点 2` 是数量标签，但没有说明是否存在未读概念。

建议未来的警示以独立事件呈现，固定包含来源直播间、发生时间、警示类型、AI 提炼、对应 ASR 原文入口和置信信息。

### P1：异常和恢复路径缺失

缺少下播、要求登录、页面加载失败、音轨消失、ASR 超时、系统负载过高以及客户端重启后的恢复状态。第一版至少需要定义用户看到的提示、可执行动作，以及其他直播间不会受影响的反馈。

## 视觉问题

### 圆角使用过多

当前方案在外层方案容器、直播间列表项、导航图标、频道容器、播放器标签、警示块和事件块上重复使用圆角，造成所有元素都像独立卡片，层级反而不清楚。

后续视觉硬约束：

- 内容区、列表项、播放器、ASR 行、警示条和状态块使用直角。
- 列表通过行高、留白、细分割线和选中底色建立层级。
- 不使用卡片嵌套，不把每条直播间做成浮动卡片。
- 圆角仅允许用于顶部页头或菜单浮层，建议半径不超过 `6px`。
- 状态标签优先用图标、颜色点和短文字，不使用胶囊形标签。

### 信息密度与层级

1. 左侧栏过窄，主播名称、运行状态和操作难以同时容纳。
2. 原型内文字过小，状态信息依赖细小灰字。
3. 播放器使用约 `2:1` 比例，与常见直播画面比例不一致。
4. 深色导航、灰色背景、蓝色选中和多层边框同时出现，边界数量过多。
5. 使用字符代替真实图标，含义和点击范围不稳定。

建议桌面主界面采用三段式结构：左侧直播间与监看队列、中部实时 ASR、右侧可收起播放器或运行详情。播放器按 `16:9` 保持稳定尺寸。导航和操作使用统一图标库并提供工具提示。

## 三个方案的处理建议

| 方案 | 定位 | 结论 |
| --- | --- | --- |
| A 主控台 | 日常添加、监看、查看单路 ASR 和播放音视频 | 作为第一版主界面，但需重做状态与操作模型 |
| B 多频道墙 | 同时横向扫读多路 ASR | 保留为后续可切换视图，不作为默认主页 |
| C 事件时间线 | 聚合重点观点和警示并回溯证据 | 纳入完整产品规划，当前 ASR 阶段先预留入口 |

## 无障碍风险

1. 方案卡片及内部模拟控件均为非语义化元素，键盘用户无法可靠操作。
2. 多个状态主要依赖蓝、绿、橙颜色区分，需要同时提供图标和文字。
3. 灰色小字可能存在对比度和字号风险。
4. 图标按钮缺少可见标签或辅助名称。
5. 实时 ASR 持续追加时，需要避免焦点跳动，并提供暂停自动滚动能力。

截图无法证明键盘焦点、读屏播报和实际对比度是否达标，这些需要在交互原型和客户端实现阶段验证。

## 下一版视觉稿必须回答的问题

1. 用户如何从“已开播”明确加入静默监看？
2. 用户如何知道每一路仍在内录和 ASR？
3. 用户如何只播放一路声音，并清楚理解切换后其他路不中断？
4. 查看某直播间是否会改变监看或播放状态？答案必须是否定的。
5. 下播、无音频和负载过高时，用户可以做什么？
6. ASR 原文和未来 AI 警示如何在视觉上保持来源清晰？
